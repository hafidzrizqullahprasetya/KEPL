\chapter{Dasar Teori}

\section{Konsep Multi-Stage Build pada Docker}
Pada pendekatan konvensional \textit{single-stage}, seluruh perkakas build (compiler, paket \textit{development header}, dan manajer paket seperti Composer) sering kali ikut masuk ke satu image akhir \cite{docker-docs}. Image yang dihasilkan menjadi besar karena berkas sementara dan pustaka kompilasi terbawa sampai ke lingkungan produksi.

Pada \textit{multi-stage build}, instruksi Dockerfile dibagi ke dalam beberapa blok \texttt{FROM} yang berdiri sendiri \cite{docker-multistage}. Tahap pertama menjadi \textit{builder} yang mengunduh dependensi dan menyusun aset. Tahap kedua menjadi \textit{runtime} dan hanya menyalin hasil akhirnya (direktori \texttt{vendor} dan berkas aplikasi) dari tahap pertama, tanpa perkakas build.

\section{Prinsip Least Privilege dan Keamanan Container}
Jika Dockerfile tidak memuat instruksi \texttt{USER}, proses di dalam container berjalan sebagai \textit{root} (UID 0). Aplikasi web yang berjalan sebagai \textit{root} melanggar prinsip \textit{least privilege}, dan dampaknya lebih besar bila terjadi eksploitasi \textit{remote code execution} atau \textit{container breakout} ke mesin host \cite{docker-security}.

Direktif \texttt{USER} membuat Docker menjalankan proses dengan akun non-root, misalnya \texttt{www-data}. Laravel perlu menulis ke beberapa lokasi lokal (seperti \texttt{storage}, \texttt{bootstrap/cache}, dan berkas SQLite), jadi kepemilikan dan izin direktori tersebut harus diatur dulu sebelum proses dialihkan ke pengguna non-root.

\section{Mekanisme Pemeriksaan Kesehatan Container (Healthcheck)}
Instruksi \texttt{HEALTHCHECK} memberi tahu Docker cara memeriksa apakah aplikasi di dalam container benar-benar bisa melayani permintaan jaringan, karena proses yang masih berjalan belum tentu sanggup menjawab permintaan \cite{docker-healthcheck}.

Docker menjalankan perintah healthcheck secara berkala sesuai interval yang ditentukan. Kode keluar 0 membuat container berstatus \texttt{healthy}. Jika perintah terus mengembalikan nilai bukan nol sampai batas \textit{retries} tercapai, status container berubah menjadi \texttt{unhealthy}. Sistem orkestrasi maupun pengguna bisa memakai status ini untuk mengetahui lebih awal bahwa layanan gagal.

\section{GitHub Container Registry (GHCR)}
GitHub Container Registry adalah registri artefak OCI (Open Container Initiative) yang terintegrasi dengan GitHub Packages \cite{github-ghcr}. Lewat GHCR, pengembang bisa mendistribusikan container image dengan hak akses yang diatur per repositori atau per organisasi.

Publikasi ke GHCR bisa diotomatisasi dengan GitHub Actions secara aman, tanpa token statis pihak ketiga. Workflow cukup memakai variabel bawaan \texttt{secrets.GITHUB\_TOKEN} dengan izin \texttt{packages: write}. Jika image diberi tag commit hash (\texttt{\$\{\{ github.sha \}\}}), setiap image bisa dilacak kembali ke commit asal kodenya di repositori git (\textit{traceability}).

\section{Analisis Baseline Image (Single-Stage)}
Sebelum mengubah Dockerfile, saya menyiapkan satu Dockerfile baseline \textit{single-stage} untuk mengukur ukuran awal image aplikasi Laravel. Baseline ini memakai base image \texttt{php:8.4-cli} berbasis Debian, lalu memasang \texttt{git}, \texttt{unzip}, pustaka untuk kompilasi ekstensi, dan installer Composer lengkap di image yang sama:

\begin{lstlisting}[style=dockerstyle,caption={Dockerfile baseline single-stage sebagai pembanding.}]
FROM php:8.4-cli

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    git unzip libzip-dev libsqlite3-dev curl \
    && docker-php-ext-install pdo_sqlite zip bcmath \
    && rm -rf /var/lib/apt/lists/* \
    && curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer

COPY composer.json composer.lock ./
RUN composer install --no-dev --prefer-dist --no-interaction --no-scripts

COPY . .

RUN cp .env.example .env && \
    touch database/database.sqlite && \
    php artisan key:generate && \
    php artisan migrate --force

EXPOSE 8000
CMD ["php", "artisan", "serve", "--host=0.0.0.0", "--port=8000"]
\end{lstlisting}

Image baseline ini dibangun dengan tag \texttt{evolusi-pl-535493:single-stage}. Ukurannya di disk mencapai \textbf{940 MB}, terlalu besar untuk layanan web sekelas microservice.

\section{Perancangan Multi-Stage Dockerfile}
\texttt{Dockerfile} utama saya ubah menjadi dua tahap:
\begin{enumerate}
    \item Tahap \textit{builder} memakai base image \texttt{composer:2.8.5}. Berkas \texttt{composer.json} dan \texttt{composer.lock} disalin lebih dulu supaya layer cache Docker bisa dipakai ulang. Setelah itu \texttt{composer install} dijalankan dengan opsi \texttt{--no-dev} dan \texttt{--optimize-autoloader}, seluruh berkas aplikasi disalin, dan autoloader produksi di-dump ulang.
    \item Tahap \textit{runtime} memakai base image minimal dengan versi terkunci, yaitu \texttt{php:8.4.26-cli-alpine}. Satu-satunya ekstensi yang dipasang di tahap ini adalah \texttt{bcmath}. Hasil build dari tahap pertama disalin dengan direktif \texttt{COPY --from=builder /app /app}.
\end{enumerate}

Saya juga menambahkan pengaturan pengguna non-root dan healthcheck:
\begin{itemize}
    \item Perintah \texttt{chown -R www-data:www-data /app} dan penyesuaian izin direktori penyimpanan (\texttt{storage}, \texttt{bootstrap/cache}, dan \texttt{database}).
    \item Direktif \texttt{USER www-data} agar proses container tidak dijalankan sebagai akun root.
    \item Direktif \texttt{HEALTHCHECK} dengan interval 10 detik yang memanggil endpoint \texttt{/api/tugas} melalui utilitas \texttt{curl}.
\end{itemize}

Isi lengkap \texttt{Dockerfile} multi-stage:

\begin{lstlisting}[style=dockerstyle,caption={Dockerfile multi-stage dengan versi Alpine terkunci dan pengguna non-root.}]
# Tahap build: siapkan dependensi vendor tanpa paket dev
FROM composer:2.8.5 AS builder

WORKDIR /app

COPY composer.json composer.lock ./

RUN composer install \
    --no-dev \
    --prefer-dist \
    --no-interaction \
    --no-scripts \
    --optimize-autoloader

COPY . .

RUN composer dump-autoload --optimize --no-dev

# Tahap runtime: image minimal alpine dengan locked version dan non-root user
FROM php:8.4.26-cli-alpine

WORKDIR /app

RUN docker-php-ext-install -j$(nproc) bcmath

COPY --from=builder /app /app

RUN cp .env.example .env && \
    mkdir -p database storage/framework/sessions storage/framework/views storage/framework/cache storage/logs bootstrap/cache && \
    touch database/database.sqlite && \
    php artisan key:generate && \
    php artisan migrate --force && \
    chown -R www-data:www-data /app && \
    chmod -R 775 /app/storage /app/bootstrap/cache /app/database

USER www-data

EXPOSE 8000

HEALTHCHECK --interval=10s --timeout=3s --start-period=5s --retries=3 \
    CMD curl -f http://127.0.0.1:8000/api/tugas || exit 1

CMD ["php", "artisan", "serve", "--host=0.0.0.0", "--port=8000"]
\end{lstlisting}

\section{Pembuatan Workflow GitHub Actions ke GHCR}
Supaya container image otomatis terbit ke GitHub Container Registry saat kode digabungkan ke cabang utama, saya membuat workflow baru di \texttt{.github/workflows/docker.yml}.

Workflow berjalan di runner \texttt{ubuntu-latest} dengan izin \texttt{packages: write}. Nama image diubah ke huruf kecil karena registri OCI mewajibkan nama berhuruf kecil, lalu workflow login ke \texttt{ghcr.io} memakai token bawaan GitHub Actions. Setiap image diberi dua tag, yaitu commit hash (\texttt{\$\{\{ github.sha \}\}}) dan \texttt{latest}.

\begin{lstlisting}[style=yamlstyle,caption={Berkas workflow GitHub Actions \texttt{.github/workflows/docker.yml}.}]
name: Docker

on:
  push:
    branches: [main, dev]
  workflow_dispatch:

permissions:
  contents: read
  packages: write

jobs:
  build-and-push:
    name: Build & Push GHCR
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Siapkan nama image huruf kecil
        run: echo "IMAGE_NAME=$(echo '${{ github.repository }}' | tr '[:upper:]' '[:lower:]')" >> $GITHUB_ENV

      - name: Login ke GitHub Container Registry
        run: echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin

      - name: Build Docker image
        run: |
          docker build \
            -t "ghcr.io/${IMAGE_NAME}:${{ github.sha }}" \
            -t "ghcr.io/${IMAGE_NAME}:latest" .

      - name: Push Docker image ke GHCR
        run: |
          docker push "ghcr.io/${IMAGE_NAME}:${{ github.sha }}"
          docker push "ghcr.io/${IMAGE_NAME}:latest"
\end{lstlisting}

Cabang \texttt{main} pada repositori \texttt{evolusi-pl-535493} dilindungi aturan proteksi yang mewajibkan status check CI lulus sebelum merge. Karena itu, perubahan dikerjakan di cabang fitur dengan langkah berikut:

\chapter{Kesimpulan}
Dari praktikum dan pengujian pada pertemuan kelima, saya menarik kesimpulan berikut:
\begin{enumerate}
    \item \textit{Multi-stage build} memisahkan instalasi dependensi Composer dari tahap runtime produksi, sehingga sisa proses build tidak ikut masuk ke image rilis.
    \item Dengan base image minimal \texttt{php:8.4.26-cli-alpine}, ukuran container image turun dari 940 MB menjadi 266 MB, atau berkurang 674 MB (71,70\%).
    \item Instruksi \texttt{USER www-data} membuat container berjalan tanpa hak akses akun \textit{root}, sehingga container lebih aman.
    \item \texttt{HEALTHCHECK} memeriksa layanan web di dalam container secara otomatis, dan \texttt{docker ps} menampilkan status \texttt{(healthy)}.
    \item Workflow GitHub Actions mem-build dan mem-publish image ke GitHub Container Registry (GHCR) secara otomatis, dengan tag commit SHA dan visibilitas publik.
\end{enumerate}
