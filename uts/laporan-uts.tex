\chapter[Tujuan Ujian]{Tujuan Ujian}
Sesuai arahan pada lembar soal Ujian Tengah Semester mata kuliah \textit{Konstruksi dan Evolusi Perangkat Lunak} Semester Gasal Tahun Akademik 2026/2027, tujuan pengerjaan ujian ini adalah:
\begin{enumerate}
    \item Mahasiswa mampu merancang dan mengimplementasikan layanan backend RESTful API berbasis Laravel dengan tema mandiri yang dilengkapi otentikasi token Laravel Sanctum, operasi CRUD lengkap, dan kesesuaian kode status HTTP 201, 422, serta 401 (CPMK 1).
    \item Mahasiswa mampu membangun antarmuka web interaktif berbasis Vue.js 3 dan Axios yang terhubung ke backend, menyimpan token otentikasi pada penyimpanan lokal, mengelola data aset, dan membaca alamat API melalui variabel lingkungan (CPMK 1).
    \item Mahasiswa mampu mengelola repositori publik Git di GitHub dengan struktur \texttt{backend/} dan \texttt{frontend/}, menerapkan aturan proteksi cabang \texttt{main} dan \texttt{dev}, serta menyusun alur pengujian otomatis menggunakan GitHub Actions (CPMK 2).
    \item Mahasiswa mampu menerapkan alur penerapan berkelanjutan (\textit{Continuous Deployment}) pada GitHub Actions yang dibatasi hanya untuk cabang \texttt{main}, mengamankan konfigurasi sensitif dengan GitHub Secrets, serta mempublikasikan citra kontainer ke GitHub Container Registry (\texttt{ghcr.io}) menggunakan tag commit SHA (CPMK 3).
    \item Mahasiswa mampu menyusun berkas \textit{Dockerfile} backend dengan optimasi \textit{layer caching} dependensi Composer, serta berkas \textit{Dockerfile} frontend dengan teknik \textit{multi-stage build} berbasis Nginx yang bebas dari direktori dependensi kerja (CPMK 4 dan CPMK 5).
\end{enumerate}

\chapter{Dasar Teori}

\section{Arsitektur RESTful API dan Otentikasi Token}
Arsitektur REST (\textit{Representational State Transfer}) mengandalkan protokol HTTP standar untuk pertukaran representasi sumber daya secara terstruktur. Layanan REST bersifat \textit{stateless}, yang berarti setiap permintaan dari klien harus memuat seluruh konteks otentikasi yang diperlukan tanpa bergantung pada sesi yang disimpan di memori peladen \cite{laravel-sanctum}.

Laravel Sanctum menyediakan mekanisme penerbitan token akses pribadi (\textit{Personal Access Token}) yang efisien untuk aplikasi halaman tunggal (SPA) maupun klien mandiri. Ketika pengguna berhasil melakukan verifikasi kredensial, peladen menghasilkan string acak berbobot kriptografis dan menyimpannya dalam bentuk hash di basis data. Klien menyimpan nilai teks biasa dari token tersebut dan menyertakannya pada tajuk HTTP \texttt{Authorization: Bearer <token>} pada setiap permintaan berikutnya. Penerapan kode status HTTP baku menjadi penanda kepatuhan arsitektur, seperti 201 saat data berhasil dibuat, 422 saat validasi masukan tidak terpenuhi, dan 401 saat permintaan tidak menyertakan identitas otentikasi yang sah \cite{laravel-sanctum}.

\section{Aplikasi Halaman Tunggal dan Klien HTTP Reaktif}
Kerangka kerja Vue.js 3 mengusung paradigma reaktif berbasis komponen yang memungkinkan pembaruan antarmuka pengguna secara modular tanpa perlu memuat ulang seluruh halaman peramban \cite{vuejs}.

Integrasi antara komponen visual dan peladen REST dijembatani oleh pustaka Axios. Melalui mekanisme pencegat permintaan (\textit{request interceptor}), token yang tersimpan di \texttt{localStorage} dapat disisipkan secara konsisten pada tajuk setiap panggilan jaringan. Sebaliknya, pencegat respons (\textit{response interceptor}) bertugas mendeteksi kode status 401 guna membersihkan data sesi lokal ketika otentikasi kedaluwarsa. Standar rekayasa perangkat lunak mengharuskan alamat URL peladen dipisahkan dari logika komponen dan dibaca melalui berkas konfigurasi lingkungan (\textit{environment variable}) \cite{axios}.

\section{Manajemen Repositori Git dan Proteksi Cabang}
Dalam metodologi pengembangan perangkat lunak modern, cabang \texttt{main} berfungsi sebagai representasi kode produksi yang stabil, sedangkan cabang \texttt{dev} digunakan untuk konsolidasi fitur yang sedang dikembangkan. Pekerjaan penambahan modul baru diisolasi pada cabang fitur dan diintegrasikan melalui \textit{Pull Request} (PR) \cite{github-protection}.

Fitur \textit{Branch Protection Rules} di GitHub memungkinkan penegakan kebijakan integrasi dengan melarang pengunggahan langsung (\textit{direct push}). Kebijakan ini mewajibkan seluruh pengujian terotomatisasi (\textit{status checks}) berstatus lulus sebelum perubahan diizinkan untuk digabungkan, sehingga mencegah masuknya kesalahan regresi ke cabang utama \cite{github-protection}.

\section{Otomatisasi Alur Kerja dengan GitHub Actions}
GitHub Actions menyediakan infrastruktur otomatisasi siklus hidup perangkat lunak yang merespons berbagai kejadian pada repositori. Alur kerja didefinisikan dalam format deklaratif YAML pada direktori \texttt{.github/workflows/} \cite{github-actions}.

Pemisahan tugas antara pengujian backend (\textit{backend test}) dan kompilasi frontend (\textit{frontend build}) memungkinkan eksekusi secara paralel guna mempercepat umpan balik. Pada tahap lanjutan, tahap penerapan (\textit{deploy job}) dikonfigurasi secara bersyarat sehingga hanya dieksekusi saat kode berhasil digabungkan ke cabang \texttt{main}, sedangkan pada cabang lain alur kerja otomatis berhenti setelah pengujian selesai \cite{github-actions}.

\section{Kontainerisasi dan Optimasi Dockerfile Multi-Stage}
Teknologi kontainer Docker mengisolasi aplikasi beserta pustaka pendukungnya ke dalam satu kesatuan citra yang dapat dijalankan secara konsisten di berbagai lingkungan \cite{docker-multistage}.

Penyusunan berkas \textit{Dockerfile} yang efisien memanfaatkan prinsip pengurutan lapisan (\textit{layer caching}). Dengan menyalin berkas dependensi seperti \texttt{composer.json} dan \texttt{package.json} sebelum menyalin kode sumber aplikasi, tahap pengunduhan pustaka tidak perlu diulang selama manifes dependensi tidak berubah. Pada frontend, teknik \textit{multi-stage build} memisahkan tahap kompilasi berbasis Node.js dari tahap penyajian statis berbasis peladen Nginx yang berukuran ringkas, sehingga berkas sementara dan dependensi pembangun tidak ikut terbawa ke citra produksi \cite{docker-multistage,nginx}.

\section{Backend Laravel RESTful API (CPMK 1)}

\subsection{Perancangan Skema Data dan Model}
Sumber daya utama pada backend adalah \texttt{Asset}. Tabel \texttt{assets} dirancang untuk menyimpan atribut nama perangkat, kode inventaris unik, kategori, status operasional, nilai perolehan, dan lokasi laboratorium. Struktur migrasi basis data ditunjukkan pada Listing \ref{lst:migration-asset}.

\begin{lstlisting}[style=phpstyle,caption={Migrasi skema tabel assets pada backend Laravel.},label={lst:migration-asset}]
Schema::create('assets', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->string('code')->unique();
    $table->string('category');

Model \texttt{Asset} dilengkapi atribut \texttt{\$fillable} guna mencegah anomali \textit{mass assignment}, serta \textit{type casting} agar atribut harga terkonversi menjadi format desimal presisi pada respons JSON.

\subsection{Otentikasi Token Laravel Sanctum}
Modul otentikasi dikelola oleh \texttt{AuthController}. Pengguna masuk ke sistem melalui rute publik \texttt{POST /api/login}. Jika kredensial cocok, peladen menerbitkan token teks biasa menggunakan metode \texttt{createToken()} dari trait \texttt{HasApiTokens}. Token tersebut dikembalikan ke klien bersama data identitas dasar pengguna.

Seluruh rute sumber daya dilindungi oleh middleware \texttt{auth:sanctum}. Apabila rute privat diakses tanpa menyertakan token atau dengan token yang tidak sah, penanganan pengecualian pada \texttt{bootstrap/app.php} secara otomatis mengembalikan respons JSON dengan status \textbf{401 Unauthorized}. Rute \texttt{POST /api/logout} mencabut token aktif dari basis data sehingga token tersebut tidak dapat digunakan lagi.

\subsection{Implementasi Endpoint dan Status Code HTTP}
Operasi data pada \texttt{AssetController} mengembalikan kode status HTTP standar yang presisi:
\begin{enumerate}
    \item \texttt{200 OK}: Dikembalikan saat memuat daftar aset (\texttt{GET /api/assets}), detail satu aset (\texttt{GET /api/assets/\{id\}}), memperbarui data (\texttt{PUT /api/assets/\{id\}}), dan menghapus data (\texttt{DELETE /api/assets/\{id\}}).
    \item \texttt{201 Created}: Dikembalikan saat pembuatan entitas aset baru berhasil disimpan ke basis data (\texttt{POST /api/assets}).
    \item \texttt{422 Unprocessable Content}: Dikembalikan saat data yang dikirimkan tidak memenuhi aturan validasi (seperti nama kosong, kode duplikat, atau format harga negatif).
    \item \texttt{401 Unauthorized}: Dikembalikan saat rute privat diakses tanpa Bearer Token yang sah.
\end{enumerate}

\section{Frontend Vue.js dan Axios (CPMK 1)}

\subsection{Konfigurasi Variabel Lingkungan}
Untuk memenuhi ketentuan soal 2.c, alamat basis API tidak ditulis mati di dalam kode komponen. Alamat tersebut dikonfigurasi melalui berkas \texttt{.env} dan diakses melalui \texttt{import.meta.env.VITE\_API\_BASE\_URL}, seperti ditunjukkan pada Listing \ref{lst:vue-api-client}.

\begin{lstlisting}[style=bashstyle,caption={Konfigurasi klien Axios dengan pembacaan variabel lingkungan.},label={lst:vue-api-client}]
import axios from 'axios';

const apiBaseUrl = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000/api';

const apiClient = axios.create({
  baseURL: apiBaseUrl,
  headers: {
    'Accept': 'application/json',
    'Content-Type': 'application/json',
  },
});

apiClient.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('auth_token');
    if (token) {
      config.headers.Authorization = `Bearer ${token}`;
    }
    return config;
  },
  (error) => Promise.reject(error)
);

apiClient.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response && error.response.status === 401) {
      localStorage.removeItem('auth_token');
      localStorage.removeItem('auth_user');
      window.dispatchEvent(new CustomEvent('auth:unauthorized'));
    }
    return Promise.reject(error);
  }
);

export default apiClient;
export { apiBaseUrl };
\end{lstlisting}

\subsection{Pipeline Continuous Integration (CI)}
Alur kerja integrasi berkelanjutan didefinisikan pada berkas \texttt{.github/workflows/ci.yml}. Berkas ini memuat dua pekerjaan pengujian yang berjalan secara paralel:
\begin{enumerate}
    \item \textbf{Backend Test:} Menyiapkan lingkungan PHP 8.4, memasang dependensi Composer dari cache, menginisialisasi basis data SQLite lokal, menjalankan migrasi, dan mengeksekusi \texttt{php artisan test}.
    \item \textbf{Frontend Build:} Menyiapkan lingkungan Node.js 20, memasang pustaka menggunakan \texttt{npm ci}, dan memverifikasi kompilasi aset melalui \texttt{npm run build}.
\end{enumerate}

\section{Continuous Deployment ke GHCR (CPMK 3)}
Soal nomor 4 mewajibkan penambahan pekerjaan penerapan (\textit{deploy job}) pada alur kerja GitHub Actions guna mempublikasikan citra kontainer ke GitHub Container Registry (\texttt{ghcr.io}).

\subsection{Pembatasan Eksekusi Deploy pada Cabang Utama}
Pekerjaan penerapan dikonfigurasi agar hanya berjalan saat terjadi peristiwa pengunggahan (\textit{push}) ke cabang \texttt{main}. Pada pengujian Pull Request atau cabang \texttt{dev}, pekerjaan deploy dilewati secara otomatis. Potongan logika eksekusi tersebut ditunjukkan pada Listing \ref{lst:deploy-job}.

\begin{lstlisting}[style=yamlstyle,caption={Konfigurasi bersyarat pada pekerjaan deploy di ci.yml.},label={lst:deploy-job}]
deploy:
  name: Deploy to GHCR
  needs: [backend-test, frontend-build]
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
\end{lstlisting}

\section{Penyusunan Dockerfile Backend dan Frontend (CPMK 4 dan CPMK 5)}
Soal nomor 5 menuntut penyusunan berkas \textit{Dockerfile} untuk backend dan frontend dengan standar optimasi kontainerisasi industri.

\subsection{Dockerfile Backend dengan Optimasi Layer Caching}
Berkas \texttt{backend/Dockerfile} menggunakan citra dasar resmi \texttt{php:8.4-cli-alpine} yang eksplisit dan bebas dari tag \texttt{latest}. Untuk memanfaatkan mekanisme \textit{cache} lapisan Docker secara optimal, berkas manifes dependensi \texttt{composer.json} dan \texttt{composer.lock} disalin terlebih dahulu, diikuti proses instalasi pustaka Composer. Kode sumber aplikasi baru disalin pada lapisan berikutnya, seperti disajikan pada Listing \ref{lst:dockerfile-backend}.

\begin{lstlisting}[style=dockerstyle,caption={Berkas backend/Dockerfile dengan optimasi layer caching Composer.},label={lst:dockerfile-backend}]
FROM php:8.4-cli-alpine

WORKDIR /var/www/html

RUN apk add --no-cache \
    curl \
    git \
    unzip \
    libzip-dev \
    sqlite-dev \
    libpng-dev \
    oniguruma-dev \
    libxml2-dev \
    linux-headers \
    && docker-php-ext-install -j$(nproc) \
    pdo \
    pdo_sqlite \
    mbstring \
    xml \
    zip \
    bcmath

COPY --from=composer:2.8 /usr/bin/composer /usr/bin/composer

COPY composer.json composer.lock ./
RUN composer install --no-dev --no-scripts --no-autoloader --prefer-dist

COPY . .

RUN composer dump-autoload --optimize \
    && cp -n .env.example .env || true \
    && touch database/database.sqlite \
    && php artisan key:generate --force \
    && chown -R www-data:www-data storage bootstrap/cache database

EXPOSE 8000

CMD ["php", "artisan", "serve", "--host=0.0.0.0", "--port=8000"]
\end{lstlisting}

\subsection{Dockerfile Frontend Multi-Stage Build}
Berkas \texttt{frontend/Dockerfile} mengimplementasikan arsitektur \textit{multi-stage build}. Pada tahap pertama (\texttt{builder}), citra menggunakan \texttt{node:20-alpine} untuk memasang pustaka dependensi dan mengompilasi aset web produksi melalui \texttt{npm run build}. Pada tahap kedua, citra produksi menggunakan peladen \texttt{nginx:1.27-alpine}. Berkas hasil kompilasi dari direktori \texttt{/app/dist} disalin ke direktori publik Nginx (\texttt{/usr/share/nginx/html}), sedangkan direktori \texttt{node\_modules} ditinggalkan pada tahap pembangun. Pendekatan ini menghasilkan citra kontainer akhir yang bersih dan berukuran minimal, sebagaimana dicantumkan pada Listing \ref{lst:dockerfile-frontend}.

\begin{lstlisting}[style=dockerstyle,caption={Berkas frontend/Dockerfile menggunakan teknik multi-stage build.},label={lst:dockerfile-frontend}]
FROM node:20-alpine AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

FROM nginx:1.27-alpine

RUN rm -rf /usr/share/nginx/html/*
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
\end{lstlisting}

\chapter{Kesimpulan}
Berdasarkan seluruh tahapan perancangan, implementasi, dan pengujian yang telah diselesaikan pada Ujian Tengah Semester mata kuliah Konstruksi dan Evolusi Perangkat Lunak, dapat ditarik beberapa kesimpulan:
\begin{enumerate}
    \item Layanan backend berbasis Laravel RESTful API berhasil dibangun dengan tema Sistem Manajemen Aset Laboratorium. Otentikasi berbasis token Laravel Sanctum berhasil memproteksi seluruh rute privat, dengan kepatuhan kode status HTTP standar (201 Created, 422 Unprocessable Content, 401 Unauthorized, dan 200 OK) yang terbukti melalui 13 pengujian otomatis berstatus lulus dan koleksi Postman yang lengkap (CPMK 1).
    \item Antarmuka frontend berbasis Vue.js 3 dan Axios berhasil mengintegrasikan alur login, persistensi token pada penyimpanan lokal, dan operasi CRUD aset secara reaktif. URL basis API berhasil dikonfigurasi secara dinamis melalui variabel lingkungan \texttt{VITE\_API\_BASE\_URL} (CPMK 1).
    \item Repositori sistem berhasil dikelola pada repositori publik GitHub \texttt{uts-p1-535493} dengan struktur direktori \texttt{backend/} dan \texttt{frontend/}. Kebijakan \textit{Branch Protection Rules} berhasil ditegakkan pada cabang \texttt{main} dan \texttt{dev} untuk mewajibkan alur Pull Request dan verifikasi kelulusan pengujian CI sebelum kode digabungkan (CPMK 2).
    \item Alur penerapan berkelanjutan (\textit{Continuous Deployment}) berhasil dikonfigurasi pada alur kerja GitHub Actions. Pekerjaan deploy berhasil dibatasi hanya untuk kejadian push ke cabang \texttt{main}, mengamankan variabel sensitif menggunakan GitHub Secrets, dan mempublikasikan citra kontainer ke GitHub Container Registry (\texttt{ghcr.io}) dengan tag commit SHA penuh (CPMK 3).
    \item Kontainerisasi sistem berhasil dioptimalkan melalui penyusunan \textit{Dockerfile backend} dengan strategi \textit{layer caching} dependensi Composer, serta \textit{Dockerfile frontend} yang menerapkan arsitektur \textit{multi-stage build} berbasis Nginx tanpa menyertakan direktori \texttt{node\_modules} pada citra akhir (CPMK 4 dan CPMK 5).
\end{enumerate}
